01导读与设计定位

本文档是 Monochrome 作为 tModLoader 通用能力库 的完整构建蓝图。它把此前确定的分层架构、受管 Hook 层、开发期诊断系统，与本次开放讨论的效果系统、图形管线、数学/物理工具全部整合成一份可执行的模块清单、优先级与工程规范。

1.2 三条铁律式的定位

窄而稳，不做全能库

每一个模块都要能承诺「跨 tML 版本不炸」。宁可少一个功能，不要多一个不可维护的模块。参照 Luminance 的教训：28 个 Graphics 类型已经是维护成本的上限。

可选依赖，永不强迫玩家

凡涉及第三方（Luminance / Daybreak / FargowiltasSouls）的能力一律走 weakReferences + TryGetMod 守卫，缺失时功能降级而非崩溃。

性能是接口设计的一部分

零热路径分配、SoA 存储、句柄代替引用、脏标记代替轮询。性能红线不是优化项，是设计约束（见第 18 章）。

1.3 双通道分发模型

tModLoader 没有模组级包管理器。tModLoader.targets 只会自动挂载 tModCodeAssist 一个分析器，其余编译期工具无处投递。因此必须区分两条互不重叠的通道：

通道载体触达对象放什么
运行时通道Monochrome .tmod玩家 + 开发者所有在游戏里跑的逻辑：状态系统、伤害管线、图形管线、UI 控件、物理
编译期通道独立 NuGet 包 / msbuild-sdk仅开发者Publicize 引用、Roslyn 分析器、SourceGen 契约、代码风格约束

Daybreak 的 src\global.json 里 "Tomat.Terraria.ModLoader.Sdk": "2.1.0" 正是第二条通道的实证——它真正的威力来自 msbuild-sdk + 两个 Roslyn 分析器工程，而不是 mod 本体。Monochrome 学这个模型，但P5之后再落地。

02设计哲学与跨游戏参考系

tModLoader 本身只提供「内容注册」和「钩子」两件事。所有系统性的玩法能力——状态叠加、伤害阶段、布局引擎、物理——都必须在模组层重建。而这些问题在别的游戏里已经被反复解决过，直接借成熟的抽象，比从 tML 的钩子缝合要可靠得多。

2.2 由此推导出的五条架构原则

① 定义（Def）与实例（Instance）分离

所有可叠加系统都用「不可变 Def 数据 + 紧凑实例结构体」两层。Def 进注册表（便于校验、序列化、网络索引），Instance 进 SoA 数组（便于遍历与批处理）。RimWorld / Factorio 都是这个模式。

② 修改器链（StatPart）优于硬编码分支

最终数值 = 按固定顺序跑一串 IStatPart。顺序固定、可枚举、可 dump，出问题能直接看出是哪一环导致的。这是 RimWorld 最值得抄的一点。

③ 数据驱动 + 代码兜底

定义可以从 hjson/json 读（开发期热重载），也可以在 C# 里注册（发布期）。二者同一套 Def 结构，避免「配置和代码两套真相」。

④ 能力探测优于版本断言

跨模组不写「要求 Luminance ≥ 1.0.3」，而写「探测 Luminance 是否提供 X 命令」。tML 的版本号没有 ranges 语义，硬断言必然误伤。

⑤ 每个系统自带 dump / 可视化

状态系统能 dump 某实体的状态栈，伤害系统能 dump 上一次伤害的完整阶段流水，UI 能 dump 元素树，物理能画出约束线。这是第 15 章诊断系统的落地方式，也是库模组最难被替代的价值。

关键的取舍提醒

跨游戏借设计时，只借抽象、不借复杂度。例如 Dota 的 Modifier 系统有 200+ 条规则，Monochrome 只需要其中最核心的 8 条（叠加模式、互斥组、优先级、驱散类别、生命周期、到期策略、来源归属、可见性）。规则表一旦超过 20 条，基本可以判断这个模块设计过头了。

3.3 命名空间规范（修正已有问题）

已修复 · 记录为规范

此前 MonoUtil 被声明为两个命名空间下的 static partial class（...MonoUtil.Hook 与 ...MonoUtil.Mathematics）。partial 要求同一命名空间，跨命名空间就是两个不同类型，消费者同时 using 两者会得到 CS0104 二义性。现已统一为单一命名空间 Monochrome.Common.MonoUtil，按目录用 partial 分文件。规范固化如下：

  • 命名空间 = 目录路径，一一对应，不允许「目录 A 里放命名空间 B」。
  • 同名 partial 类型必须同命名空间；跨目录分类用 partial 分文件，不靠命名空间分层。
  • 公开 API 的类型名不要重复。若确有多个同名概念（MonoHook 的工具类与数据类），用后缀区分（MonoHookUtil / MonoHookInfo）。
  • 不要留空的 <Folder Include> 占位。目录存在即由文件体现；空声明只会让目录结构与命名空间脱节。

04核心基础层

4.1 子系统注册表与生命周期

避免 tML 的 ModSystem 与静态状态互相踩踏。采用显式顺序：

Load→ RegisterDefs→ PostSetupContent→ HookInstall→ Ready→ Unload→ HookRemoveAll→ DisposeBuffers 
public interface IMonoService
{
    int Order { get; }                 // 越小越先初始化；同序按注册顺序
    void Load(Mod mod);
    void RegisterDefs();               // 只注册数据，不产生运行时状态
    void PostSetup();
    void InstallHooks();               // 与 tML 的 MonoModHooks 交互
    void Unload();                     // 必须与 Load 对称，勿漏
}

要点：Unload 必须与 Load 严格对称。诊断系统在卸载时断言「注册表已空」，能提前抓住热重载泄漏——这是 tML 最典型的崩溃来源。

4.2 事件总线

  • 按帧阶段分派，而非一个 OnUpdate：PreUpdate / WorldUpdate / PostUpdate / PreDraw / PostDraw / PostDrawInterface。
  • 弱订阅（弱引用或显式 token），避免模组卸载后回调仍被持有 → 访问已卸载类型 → TypeLoadException。
  • 零分配派发：用 List<T> + 反向遍历 + 版本号判断，杜绝派发中修改集合的异常。
  • 提供 只读的订阅者 dump，诊断时能看到「谁在监听什么」。

4.3 对象池与零分配

// 结构体句柄 + 索引池：避免装箱、避免 GC 压力、天然可序列化
public readonly struct Handle { public readonly int Index, Version; }

public sealed class Pool<T> where T : struct
{
    T[] _items; int[] _versions; int _free;      // 空闲链表用 int 数组实现
    public Handle Rent(out Span<T> slot);
    public bool TryGet(Handle h, out int index); // 校验 Version，杜绝悬垂句柄
    public void Return(Handle h);
}

分配红线参考值（每帧 60fps，预算 ~2ms 用于所有库系统）：粒子系统 < 4KB/帧，状态系统 0 B/帧稳态，UI 布局 0 B/帧稳态。

4.4 确定性随机（多流）

  • 不使用 Main.rand（全局、与世界状态耦合，多人不同步）。
  • 自实现 PCG32 / xoshiro128**，纯函数式种子派生：Seed(worldSeed, entityId, tick, purpose)。
  • 分流域：视觉特效 / 玩法判定 / 程序生成各自独立流，避免「多加一个粒子导致掉落物变化」。
  • 多人同步的随机必须由服务端产出并通过 ModPacket 广播，或保证同种子同序列。

4.5 调度器与时间轴

能力用途实现要点
Delay(ticks, action)替代手写计时器字段最小堆 + 帧号，每帧只处理到期项
TimelineBoss 战阶段编排、过场演出关键帧 + 插值通道 + 可暂停/可缩放/可倒放
TweenUI/实体数值缓动缓动函数表 + 目标 setter 委托 + 池化
Coroutine分帧长流程（如多阶段攻击）引用 Monocle 思路：迭代器 + 返回等待条件
时间基准要统一

tML 里 Main.GameUpdateCount（世界 tick）、Main.GlobalTimeWrappedHourly（真实时间）、Main.dayTime（游戏日）是三个不同时钟。所有库模块必须显式声明用哪个，混用会导致暂停、单人多人差异、以及「切出窗口后物理爆炸」。推荐：玩法逻辑一律用 tick，纯视觉用真实时间并 clamp dt。

05Buff / 状态效果系统 核心模块

tML 的 Buff 只提供「一个槽位 + 一个剩余时间」，player.AddBuff 的语义是刷新时间。任何「层数 / 强度随层数增长 / 每层独立计时 / 互斥 / 驱散 / 光环」都必须自己实现。这是玩法模组最普遍、最反复被重写的痛点，也是 Monochrome 最有价值的模块。

5.1 设计目标

统一载体

Buff、Debuff、DoT、光环、被动、临时增益全部建模为同一种 StatusInstance，只是 Def 参数不同。参照 Dota 的 Modifier。

层数语义可配

一个 StackMode 枚举覆盖 Additive / Extend / Independent / Amplify 四种主流语义。

与 tML 可视化兼容

复用原版 ModBuff 图标与提示，不重造 UI；层数显示用 Buff 名称后缀或图标角标。

5.2 三层数据模型

StatusDef 不可变 · 注册表

ID、显示、最大层数、层数模式、每层增量、基础时长、互斥组、优先级、驱散类别、抗性标签、生命周期钩子。全局唯一，可序列化为网络短索引。

StatusInstance 结构体 · SoA

仅 5 个字段：OwnerId / DefIndex / Stacks / EndTick / NextTick。按 Def 分组存储，未激活的 Def 不参与遍历。

StatBlock 派生结果

所有实例按固定顺序跑一遍 IStatPart 得到的聚合数值。发生变化时置脏，仅重算一次。

5.3 层数模式（StackMode）

模式再次施加时的行为强度变化典型用途
Refresh重置持续时间，层数不变无普通增益、原版风格
Extend剩余时间累加，有上限无可叠加时长的抗性
Amplify层数 +1，时间刷新线性 1 + (n-1)*step中毒/灼烧/冰霜层数
Independent新增一个独立实例（各有自己的时间）每层完全独立多来源 DoT（不同玩家施加的出血）
Diminishing层数 +1，但第 n 层效果 1/(1+k(n-1))递减控制类效果（眩晕递减，参考 WoW DR）

5.4 叠加与互斥规则

参照 Minecraft 属性操作序与 RimWorld 的 StatPart —— 顺序固定是这套设计最重要的性质，因为它让「为什么最终是 37%」变成可枚举、可 dump 的问题。

// 固定五段，按序执行
// 1. FlatAdd      : 所有层数 × 每层固定值，求和
// 2. PercentAdd   : 所有「increased」类来源求和 → (1 + sum)
// 3. PercentMul   : 每个「more」类来源独立相乘 → Π(1 + p_i)
// 4. Override     : 有 Override 标记的来源直接覆盖（只有一个生效，取最高优先级）
// 5. Clamp        : 上下限裁剪（防无敌 / 防负值反伤）

public interface IStatPart { void Apply(ref StatContext ctx); }
为什么把 increased / more 分开

这是 PoE 二十年验证过的结论：如果全用加法，玩家堆同一种属性会迅速崩坏；如果全用乘法，收益又过于稳定没有构筑感。加法池（increased）让同源堆叠有边际递减，独立乘区（more）让异源组合有爆发空间。两者必须有明确的、写在文档里的区分规则，否则模组作者会随意选择并制造出无法平衡的数值。

5.7 网络同步

这是整套系统里最容易出事的地方
  • 只同步「变更事件」，不同步「完整状态」（每秒 60 次全量同步会直接吃掉带宽）。
  • 事件格式：[OwnerKind][OwnerId][DefIndex(short)][Op][Stacks][Duration]，Op 用 1 字节编码 Apply/Stack/Remove/ClearAll。
  • DefIndex 必须是短索引，不能传字符串 ID。
  • 服务端权威：客户端只发「请求施加」，实际结算在服务端完成并广播结果。纯视觉状态（如命中特效）走 NetMessage 或本地预测。
  • 玩家中途加入时，需要一次性的全量快照同步（在 SyncPlayer 阶段）。
  • DoT 的每 tick 伤害必须由服务端结算，否则多人下伤害不一致。

5.8 性能设计

  • SoA + 按 Def 分桶：tick 遍历只走「有实例的 Def」，无实例的 Def 完全不进循环。
  • GlobalNPC / ModPlayer 条件挂载：无任何状态时，全局钩子里第一行就 return，成本约 1 个布尔判断。
  • StatBlock 缓存 + 脏标记：只在层数/时长/来源集合变化时重算；普通帧零成本。
  • 时长用绝对 tick，不用倒计时递减（避免暂停/多人的累计误差）。
  • 目标上限：单实体状态实例数上限（建议 64），超限时按优先级淘汰并打日志。

为什么「多层减伤 + 封顶 + 保底 + 穿透」这个组合是对的
  • 只有多层：作者能分别调「护甲」「元素抗性」「阶段减伤」，不会一改就崩坏其他维度。
  • 必须有封顶：任意多个来源相乘会趋近 100%，玩家遇到的就是「打不动」而不是「很难打」。
  • 必须有保底：防止免疫判定泄漏（例如某条件组合导致减伤 = 100%）造成无法通关。
  • 必须有穿透：否则减伤系统会不可逆地压制掉所有「破防」类玩法设计。

四者缺一，这个系统就会从「便利」变成「麻烦」。

6.3 玩家侧防御

  • 护盾层（吸收值是独立池，先扣护盾再扣血，护盾有独立时长与来源）。
  • 伤害延迟结算（DoT 式缓冲：受击后把伤害摊到 N tick 内分摊扣除，给玩家反应窗口）。
  • 无敌帧管理：多个来源的无敌需求取并集而非互相覆盖（tML 的 immuneTime 是单一值，容易被后写入者顶掉）。
  • 闪避/免伤判定要在最早期阶段，避免后续阶段产生副作用（例如吸血、反伤被误触发）。

6.4 伤害类型与抗性

6.5 数值反馈

  • 浮动伤害数字：可配置为原版风格 / 自定义（描边、暴击放大、元素着色）。
  • 减伤生效提示：当 D3–D8 实际削减超过阈值时显示「格挡 / 抗性 / 无效」类反馈，否则玩家无法理解为何伤害不高。
  • 诊断模式：开关打开后，每次伤害在聊天栏或控制台 dump 完整阶段流水（哪个规则砍掉了多少）。这是本系统最有价值的功能

6.6 性能红线

  • 伤害管线只在命中时执行，不在每帧执行 —— 因此可以用稍微「重」的实现，但禁止在其中分配（每次命中触发 GC 在弹幕海下会很明显）。
  • 规则查找用「按 NPC 类型预编译的规则数组」而非每帧遍历全部规则。
  • 减伤规则集合在 PostSetupContent 后冻结（标记为不可变），并在诊断中报告每个 NPC 的规则条数。

8.1 同步原语

原语方向用途实现要点

8.2 关键陷阱

多人下的必踩坑
  • 不要同步字符串（每个状态 ID 传字符串，弹幕海下带宽爆炸）。用注册表的短索引。
  • 不要依赖字典遍历顺序做序列化（顺序不保证，会导致两端不同步）。
  • 不要用 Main.rand 做玩法判定（客户端和服务端序列不同）。
  • 不要相信客户端的伤害数字，服务端重算。
  • ModPacket 单包有大小限制，大快照要分片并带序号与总数字段。
  • 世界退出/重进时，所有客户端缓存必须清空 —— 在 ModSystem.OnWorldUnload 里做，别只写在 Unload。

8.3 side 决策

Monochrome 已设 side = NoSync（与 Daybreak、LiquidSlopesPatch 一致）。含义是不自动同步——所有网络行为必须手写，不会被 tML 的自动同步机制拖累。这对库模组是正确的默认值：库不应该替消费者猜同步策略。

但要在文档中明确代价：消费者若需要同步，必须自己调 MonoNet 的 API；Monochrome 不提供「自动同步字段」的隐式魔法（那种魔法在库模组里几乎必然产生难以定位的多人 bug）。

哈希整数/坐标哈希 → 确定性随机同一瓦片永远得到同一扰动值（无需存储）

9.6 数值与缓动

  • 缓动全表：Linear / Quad / Cubic / Quart / Quint / Sine / Expo / Circ / Elastic / Back / Bounce，各含 In/Out/InOut（共 31 个），外加 Step、Bezier、Spring。
  • 弹簧阻尼（Damped Spring）：SpringTo(current, target, ref velocity, stiffness, damping, dt)。比缓动函数更适合「目标会动的跟随」场景（相机、UI 指示器）。
  • 通用工具：Remap / SmoothStep / SmootherStep / MoveTowards / LerpAngle / Approach / InverseLerp / Wobble。
  • 定点数 可选：Fix64 用于确定性模拟。仅在需要帧级可复现的多人模拟时引入，否则是纯负担。
本层必须建立的纪律（源于已发生的真实 bug）
  • 每个数学函数都要有一个断言或单元测试。Factorial(n) 断言 n < 13（int 阶乘 13! = 6227020800 > int.MaxValue），或直接改成 long/BigInteger。阶乘/排列组合的调用点应改用乘法形式 n*(n-1)*...*k，既避免溢出又少一次除法。
  • 向量运算不要就地改写后被后续引用。v.X = f(v.X); v.Y = g(v.X); 这种写法是隐蔽错误的温床，在本层应一律先取局部变量或返回新值。
  • 禁止 using 未使用的命名空间。此前 Geometry.cs 里有 using rail;（RailSDK）——它会给库引入无谓的命名空间污染与潜在冲突。

10物理模拟

绳索、布条、软体本质上都是同一件事：质点 + 约束 + 迭代求解。不要为每种效果写一套积分器——写一个求解器，配不同的约束拓扑。这是 Luminance 的 Common.VerletIntergration 走的路，也是唯一可维护的路。

10.1 统一约束求解器

// PBD / Verlet 统一形态：位置积分 + 约束投影 + 迭代收敛
public sealed class ParticleSolver
{
    Span<Vector2> _pos, _prev;
    List<IConstraint> _constraints;

    public void Step(float dt)
    {
        Integrate(dt);                       // 显式积分 + 阻尼
        for (int i = 0; i < Iterations; i++)  // 通常 4–12 次
            foreach (var c in _constraints) c.Project(_pos, dt);
        SolveCollisions();                   // 含瓦片碰撞（原版 Collision）
    }
}
public interface IConstraint { void Project(Span<Vector2> p, float dt); }
约束作用效果
距离约束保持两点间距绳索、布的结构/剪切
弯曲约束约束三点夹角布的挺括感、防止折叠成尖刺
锚点约束固定某点或绑定到实体绳索端点、旗帜挂点
碰撞约束推出瓦片/实体绳索不穿地
断裂约束应变超阈值时移除布条撕裂、绳索崩断

10.2 弹性绳索

  • 拓扑：N 段等长链；段长决定柔软度。
  • LOD：按屏幕距离动态减段（远处 8 段，近处 32 段），这是唯一的性能解。
  • 自碰撞：用空间哈希，且只在段数低于阈值时开启。
  • 风力：接入统一力场（见 10.5），不要各写一套。
  • 渲染：优先用顶点条带/多边形（一次 Draw），比逐段 DrawLine 快一个量级；UV 沿弧长分布才能正确贴图。

10.3 布条 / 旗帜

  • 拓扑：w × h 网格；结构约束（相邻）+ 剪切约束（对角）+ 弯曲约束（隔一个）。
  • 性能：8×12 = 96 质点已足够视觉表现；超过 16×16 的布在多人下几乎必然掉帧。
  • 自碰撞：默认关闭（O(n²)，收益远低于成本）。
  • 与风/角色移动耦合：布受的力应与角色速度相关，才会有「挥动」感。

10.4 2D 光照

方案原理成本建议
原版 Lighting.AddLight写入瓦片光照图极低默认用这个，90% 需求已满足
加法叠加绘制在实体层加一层加色混合的径向渐变低发光特效、弹幕光晕
遮挡体阴影投射从光源向遮挡多边形边缘投射，得到阴影几何中需要「光被墙挡」的表现时
SDF 光线步进渲染进 RT，逐像素沿 SDF 步进高只用于小范围高精度光照（如全屏一次）
光照贴图累加 + 后处理低分辨率 RT 累加所有光源，再上采样调制中最佳性价比，支持多光源、色温、自发光

推荐组合：原版光照作为基底 → 低分辨率 RT 累加自定义光源（含色温与半径）→ 上采样后与场景做乘法/加法混合 → 可选遮挡体投射处理「阴影」。这套方案支持任意多光源、天然支持发光体、且成本只与光源数量相关。

10.6 性能架构

物理必须遵守的四条
  • 固定时间步 + 渲染插值。用可变 dt 直接积分，一旦掉帧就会爆炸或穿模。
  • 距离裁剪：屏幕外 > 一定距离的绳索/布直接冻结（不 Step，只保留状态），回到视野内再恢复。
  • 全局预算：每帧物理总迭代次数设上限（如 20000 次约束投影），超预算的低优先级对象跳过本帧。
  • 失败降级：检测到 NaN / 速度异常时自动复位该对象并打日志，而不是让整个模拟污染成 NaN。

11图形与特效系统

11.1 三层绘制空间

这是最容易设计混乱的部分。先明确「这段绘制属于哪个空间」，再决定用什么技术。

世界层
受 Main.screenPosition 与相机变换影响。细分为：BehindNPCs / BehindProjectiles / OverPlayers / OverWorld 等 draw layer。粒子、绳索、布条、Metaball 世界实例属于这里。需要按 Y 排序时小心与 tML 绘制顺序的冲突。
屏幕层
全屏 RT 与后处理。辉光、色差、扭曲、屏幕震动属于这里。典型管线：场景 → 降采样亮部 → 多次模糊 → 与原图合成 → 输出。
UI 层
受 Main.UIScale / UIScaleMatrix 影响，坐标系与世界层完全不同。UI 用的 RT 不能与世界 RT 共用尺寸假设。见第 12 章。
最常见的图形 bug：坐标系混用

把世界坐标直接丢给 UI 绘制（或反过来）会导致「分辨率一变/缩放一改，特效就飘走」。规范：任何绘制 API 的第一个参数都必须是明确的坐标空间枚举或类型，不要靠约定。

11.2 Shader 管线

重要更正：tML 支持编译期着色器编译

此前讨论中提到的「运行时编译着色器」是 Luminance 的方案（依赖 System.IO.FileSystem.Watcher + System.Diagnostics.Process）。但 tMLMod.targets 的 AdditionalFiles 收集规则包含 *.fx，tML 构建期就会把 .fx 编译成 .xnb，运行时通过 ModContent.Request<Effect>("Mod/Effects/Foo") 加载。

因此 Monochrome 应该走编译期路线：快、无外部进程依赖、无杀软误报、无跨平台问题。不要做运行时编译。

// Assets/Effects/Glow.fx  → 构建期编译 → 运行时加载
var fx = ModContent.Request<Effect>("Monochrome/Assets/Effects/Glow",
                                    AssetRequestMode.ImmediateLoad).Value;

// 参数缓存：不要每帧按名字查 EffectParameter（字符串查找 + 字典）
sealed class GlowParams {
    public readonly EffectParameter Time, Color, Intensity;
    public GlowParams(Effect fx) {
        Time      = fx.Parameters["uTime"];
        Color     = fx.Parameters["uColor"];
        Intensity = fx.Parameters["uIntensity"];
    }
}
能力做法注意
参数缓存构造时解析并持有 EffectParameter名字拼错会在运行时静默返回 null → 加载时断言非 null
技术/Pass 选择fx.CurrentTechnique + Passes用多 Pass 而非多文件组织变体
宏/变体同一 .fx 内多个 technique，或按需编译少量变体避免组合爆炸

调试编译失败必须让构建失败并给出可读错误静默失败会变成「特效不出现」的幽灵 bug

11.5 Metaball（融合球）

Metaball 的本质是SDF 阈值的等值面提取。两种实现：

方案原理优点缺点
RT 累加 + 阈值 Shader 推荐 把所有球的影响力画进半分辨率 RT（加法混合），再用一个 shader 做 smoothstep(threshold, threshold+w, sum)，最后边缘光/内发光 球数量几乎无上限；边缘光滑；分离/融合自然 需要 RT 与 shader
CPU Marching Squares 在网格上采样 SDF 场，提取等值轮廓多边形，按普通多边形绘制 能得到真实几何体，可用于碰撞与描边 成本随分辨率平方增长；分辨率低时边缘锯齿
 
// 影响力函数：不同的"融合手感"来自不同的衰减函数
float Influence1(float d, float r) => saturate(1 - d/r);            // 线性，边界清晰
float Influence2(float d, float r) => saturate(1 - d*d/(r*r));      // 二次，更黏
float Influence3(float d, float r) => pow(saturate(1 - d/r), 3);     // 三次，聚拢

组合建议：默认用「RT 累加 + 阈值 shader」，另外提供可选的 CPU 轮廓提取用于碰撞与描边。Luminance 已有 MetaballManager；Monochrome 应做独立实现 + 可选适配，不要硬依赖。

12UI 编写系统 核心模块

tML 的 UI 建立在 UIElement 之上：有 Left/Top/Width/Height（StyleDimension，像素或百分比）、Padding、HAlign/VAlign，但没有布局引擎——一切位置靠手算，响应式几乎不可能，样式完全内联。这是模组作者抱怨最多的地方之一。

12.1 设计目标

声明式 + 布局引擎

写「这是什么、和谁怎么排」，不写「它在哪里、多少像素」。

样式与结构分离

样式对象可复用、可继承、可切换主题；控件不含外观硬编码。

保持 tML 兼容

底层仍是 UIElement，能嵌进任何现有 UIState，不要求消费者重写界面。

12.2 布局引擎（Flex 子集 + Grid 子集）

不要实现完整 Flexbox

完整 flexbox 规范有 30+ 属性与大量边界情况（基线对齐、多行反向、shrink 的迭代算法）。实现一个方向明确的子集就够了：

实现属性
Flex 子集Direction(Row/Column) · Justify(Start/Center/End/SpaceBetween/SpaceAround) · Align(Start/Center/End/Stretch) · Grow · Shrink · Basis · Gap · Wrap(仅单向) · Padding/Margin
Grid 子集固定列数 + 等宽/按比例(fr)/固定像素三种轨道 · 行列 gap · 跨列跨行
定位Absolute（相对父元素）+ Anchor(9 宫格) + Pivot
尺寸像素 / 百分比 / Auto（由内容决定）/ Fill（撑满剩余）

两趟测量即可：Measure（自底向上算期望尺寸，Auto 在此确定）→ Arrange（自顶向下分配位置，Grow/Fill 在此确定）。

  • 不要每帧轮询值比较（if (old != new)）—— 这在数值连续变化时会每帧重排。显式通知优于隐式轮询。
  • 提供 立即模式（IMGUI）备选：调试面板、内部工具用立即模式写起来快得多，不需要绑定与持久化元素树。

12.7 输入、焦点与文本

  • 事件路由：捕获（父→子）→ 目标 → 冒泡（子→父），与 DOM 一致，行为可预期。
  • 焦点管理：Tab 键顺序、键盘导航、手柄支持（tML 有手柄输入需一并处理）。
  • 文本性能：DynamicSpriteFont.MeasureString 结果必须缓存（每次调用都会做布局计算）；换行/截断结果同样缓存；文本内容变化时才失效。
  • 富文本：渐变文字、描边、内嵌图标、可点击片段 —— 需自建解析，不要试图改原版文本渲染。

12.8 与 tML 现有系统的关系

tML 系统Monochrome 的做法
UIState / UserInterface完全兼容：MonoElement 继承 UIElement，可直接 Append 到任何 UIState
ModConfig不替代。提供辅助控件与布局（把 ModConfig 塞进 Monochrome 布局里做分组/说明）

12.9 调试支持

  • 布局边界可视化：按 F 键显示所有元素的 Measure/Arrange 结果、padding/margin、溢出区域。
  • 元素树 dump：导出为缩进文本，含每层的尺寸、样式来源。
  • 重排/重绘统计：每秒多少次全量布局，找出「为什么这个界面卡」。

13内容与数据驱动

13.1 注册 DSL

// 替代 tML 的样板代码：一个类 + SetStaticDefaults + SetDefaults + ...
MonoContent.Item("CrystalBlade")
    .Texture("Assets/Items/CrystalBlade")
    .Damage(45, DamageClass.Melee)
    .UseTime(18).Knockback(6f).Rarity(ItemRarityID.Pink)
    .Tooltip("localization key 自动推导")
    .Recipe(r => r.AddIngredient(ItemID.CrystalShard, 12).AddTile(TileID.MythrilAnvil));
但不要做过头

DSL 只适合高度重复、参数固定的内容（物品、配方、简单弹幕、掉落表）。带复杂自定义逻辑的内容（Boss、复杂 ModProjectile）继续用继承，强行 DSL 化会得到一套无法调试的元编程。判断标准：如果一个内容类型的 SetDefaults 经常超过 40 行，它就不适合 DSL。

13.2 数据驱动与热重载

  • Def 可来自 hjson/json（开发期可改可热重载），也可代码注册（发布期）。同一套 Def 结构，两种来源。
  • 热重载仅限 Debug 构建 + 显式开关；发布版完全不加载文件系统监视。
  • 加载失败必须报出文件与行号，并保留上一份有效数据（不要因一个错字导致整个模组不可用）。

13.3 本地化助手

  • key 自动推导：从类型名 + 字段名生成稳定 key，避免手写字符串。
  • 完整性校验：扫描代码中的 Language.GetTextValue("...") 与 hjson 文件，报告缺失 key 与多余 key。这是最实用的一个工具
  • 占位符校验：检查 {0} / {1} 在各语言版本中是否一致（多语言下最常见的崩溃源）。
  • 与第 15 章诊断系统集成，游戏内命令输出报告。

13.4 动画系统

  • SpriteSheet 时间轴：帧序列 + 每帧时长 + 事件帧（在第 N 帧触发回调，用于命中判定/音效）。
  • 状态接入：动画状态与第 7 章的状态机解耦但可映射（状态 → 动画名）。
  • 混合/过渡：简单交叉淡化即可，不要上骨骼动画。

13.5 音频

  • 音效池 + 节流：同种音效在 N tick 内只播放一次（否则弹幕海下音频会爆掉）。
  • 音量衰减与声像：按距离衰减，按屏幕位置设左右声道。
  • 动态音乐层：Boss 战时叠加鼓点层（多首曲目同步播放，按强度切换音量）。
  • 限制：SoundEngine.PlaySound 有并发上限，超过会静默丢弃 → 必须在库层做节流而不是让消费者自己处理。

14跨模组互操作

14.1 tML 的现实

  • 唯一的跨模组 API 是 Mod.Call(object[])：字符串式、无编译期检查、无版本协商、参数类型靠约定。
  • modReferences 不传递：A 依赖 B、C 依赖 A，C 不会自动获得 B。第三方类型一旦出现在公开签名里，消费者就被迫也引用 B。
  • 版本号无语义：Name@1.7.3.9 只是一个标记，没有 ranges、没有兼容性判断。
  • weakReferences 不提供编译期可见性：Monochrome 写了 weakReferences = Luminance, Daybreak 照样能编译，但一旦写 using Luminance...; 就必须能解析到那个程序集（安装为模组 / 在 ModSources / 自己的 lib\ + HintPath）。
当前状态提醒

Monochrome 的 weakReferences = Luminance, Daybreak 目前是空转的：Luminance 既没安装为 .tmod、也不在 ModSources、Monochrome 也没有 lib\Luminance.dll（它只存在于 FPM 的 lib\ 下），Daybreak 更是只存在于 E:\Desktop\秦安模组源码收集\。这意味着现在写任何 Luminance 代码都会编译失败。要么补上可见性（推荐：Monochrome 自己的 lib\），要么先把这行删掉。

T3 编译期契约Roslyn SourceGen 生成调用桩 + 版本校验（Daybreak 路线）高契约稳定且消费者多时

14.3 公开 API 的硬规则

  1. 公开签名里只允许出现自己的类型与原版/tML 类型。第三方类型只能出现在 Compat/ 目录内的、标记为 internal 或明确标注 [ThirdPartyApi] 的适配器里。
  2. 只增不改。要改就先 [Obsolete]，至少跨一个大版本再删。
  3. 运行时自检：Load 时校验依赖版本、钩子是否挂上、资源是否齐全，不符则给出明确错误而非静默失效。
  4. 提供能力查询 API：MonoApi.HasFeature("status.independent")，让消费者能按能力分支而非按版本号分支。

14.4 复制粘贴 vs 引用 —— 必须二选一

当前方案存在结构性冲突

FargosPhantasmMode\Monochrome\README.md 定义了「把 Monochrome 源码复制进 FPM」的约定。但如果 FPM 同时 modReferences = Monochrome，就会出现 CS0433（类型同时存在于两个程序集）。

二选一：

  • 要「库」就引用 —— 硬 modReferences（或弱引用 + 守卫），零同步成本，但消费者必须装 Monochrome。
  • 要「零依赖」就复制 —— 那它就不是库模组，而是代码模板库。命名空间保持 Monochrome（已定），文档按模板写，且要保证每个文件都能独立编译（GlobalUsings.cs 已拆出 ✓）。

两种模式都合理，但不能同时存在。建议：Monochrome 本体走「库」，FargosPhantasmMode\Monochrome\ 目录明确降级为「冻结的代码快照」并停止同步。

15.3 零开销原则

发布版必须零开销
  • 整章代码用 [Conditional("DEBUG")] 或 #if DEBUG 包裹，发布构建里根本不进程序集（不是「关掉了但仍调用」）。
  • 运行期观测（PerfSampler、DamageTracer）用开关控制，默认关闭；开启时才写入环形缓冲。
  • 环形缓冲预分配，绝不动态增长（否则诊断本身会改变性能特征，观测失真）。
  • Trace 列表这类诊断字段在发布版应为 null 或空 Array.Empty，相关代码路径被 if (Trace is null) return; 短路。

15.4 为什么这个模块值得优先做

  • 它是所有其他模块的验证手段。没有 dump 能力，第 5 章的状态系统、第 6 章的伤害管线都是「黑盒」，出了问题只能靠猜。
  • 它零兼容风险。不碰渲染管线、不改游戏逻辑、不影响存档。
  • 它是库模组的差异化招牌。Diff 一个 API 容易，做一个好用的诊断工具很难被替代。
  • 它反哺文档。诊断输出的格式本身就是最好的「系统行为说明书」。

先做「能被验证的」，再做「能被使用的」。诊断系统排在第 2–3 阶段，早于状态系统和伤害管线 —— 因为后两者没有 dump 能力就无法调试。数学库同理：它是所有表现层的地基，且成本低、无兼容风险、可单元测试。

18反模式与红线

18.1 明确不要做的事

反模式为什么
运行时编译着色器 + 文件监视热重载Luminance 为此引入了 System.IO.FileSystem.Watcher 与 System.Diagnostics.Process：外部进程依赖、跨平台脆弱、杀软误报、调试困难。而 tML 构建期已支持 .fx 编译，运行时编译是纯负债
做「什么都有」的巨型工具库Luminance 的 28 个 Graphics 类型已经是维护成本上限。每一项都要能承诺跨版本不炸，模块越多这个承诺越难兑现
公开 API 里暴露第三方类型强迫消费者引用第三方，并把 Monochrome 与该第三方版本绑死。第三方类型必须隔离在 Compat/ 适配器内
替消费者挂钩子tML 的 detour 归属按钩子委托的宿主程序集判定（MonoModHooks.GetDetourList）。库替别人订阅，卸载清理就会错乱。必须导出「传入你的委托」的 API
在库内部包一层委托new ILContext.Manipulator(action) 这类套壳会让归属判定失败并抛「Cannot identify owning assembly of hook」。绝不能包
复制源码 + modReferences 并存CS0433 类型冲突。二选一
每帧字典查找 / 每帧 LINQ / 每帧字符串拼接库的调用频率远高于消费者预期，这些在库内部会被放大成灾难
全局可变静态状态tML 的热重载只保证它跟踪到的 detour 会被 Undo，静态字段不会被重置 → 二次加载时状态污染，是崩溃的经典根因
用 Main.rand 做玩法判定多人下客户端与服务端序列不同 → 不同步
依赖 weakReferences 获得编译期可见性它只保证「缺失时不报错」，不保证「存在时能用」。见 14.1
把 API 名称当契约tML 每版本重命名钩子。跨模组通信要传能力字符串，而不是依赖具体方法名

18.2 性能红线速查

场景红线
热路径（每帧 / 每实体）0 字节分配。用 GC.GetAllocatedBytesForCurrentThread() 差值验证
全局钩子（GlobalNPC/ModPlayer）无相关状态时第一行 return；O(实体 × 模组) 的固有成本不能再乘
遍历集合用 List<T> + for，不用 foreach 于接口集合；不用 LINQ
大数组传递用 Span<T>/ReadOnlySpan<T>，避免拷贝
字典查询热路径用数组索引或位掩码，字典只在冷路径
字符串热路径禁止 +、string.Format、InterpolatedStringHandler 之外的内插
对象创建池化；RenderTarget2D、Effect、BasicEffect、SpriteBatch 绝不每次 new
物理固定时间步 + 距离裁剪 + 全局迭代预算
UI布局只在脏时重算；MeasureString 必须缓存
图形见 11.10 表：Begin/End < 10，RT 切换 < 20，纹理切换 ≈ 0，纹理上传 = 0

18.3 已发生的真实错误（作为纪律来源）

这些都已修复，但必须变成规范
  1. Statistics.Factorial 循环写成 for (int i = 1; i <= N; i--)。后果：对任何 N ≥ 1 恒返回 0，且每次调用循环约 43 亿次；Permutation(n,0) / Combinatorial(n,0) 变成 0/0 抛 DivideByZeroException，BezierLerp 首次迭代即中招 → 卡死数秒后抛异常。规范：循环不变量必须被验证；数学函数必须有断言或单元测试。
  2. Geometry 的两个 operator *：vector.X = f(vector.X); vector.Y = g(vector.X); —— Y 复用了已被改写的 X，原始 Y 永久丢失。规范：向量运算禁止就地改写后被后续引用；先取局部变量或返回新值。
  3. int 阶乘在 n ≥ 13 溢出（13! = 6227020800）。规范：组合数学用乘法形式或 long/BigInteger，并文档化上限。
  4. Geometry.cs 有未使用的 using rail;（RailSDK）。规范：禁止未使用 using；库不允许引入无谓的命名空间污染。
  5. global using 全在 Monochrome.cs 里，而复制约定要求排除该文件 → 被复制出来的文件无法独立编译。规范：可复制的 global using 必须放在独立的 GlobalUsings.cs（已修复 ✓）。
  6. MonoUtil 跨两个命名空间声明为 partial → 实为两个类型，消费者同时 using 会 CS0104。规范：partial 必须同命名空间（已修复 ✓）。
  7. weakReferences 写了却无法解析到程序集 → 弱引用空转，写任何相关代码都编译失败。规范：弱引用必须配套可解析的程序集来源（lib\ + HintPath）。
  8. 单元测试缺失导致 .slnx 文件夹 Name 格式错误使整个解决方案解析失败（Name 必须形如 "/xxx/"）。规范：改动解决方案后必须验证解析。（此前也有容器目录缺 build.txt 被当作假模组、吞掉嵌套 .cs 导致 6527 条 CS0246。）
